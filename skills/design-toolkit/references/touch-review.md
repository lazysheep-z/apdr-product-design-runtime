# 触屏设计与去 AI 味审查

## 按设备判定

- Web：使用 CSS px，检查实际点击区域、间距、按压反馈和不依赖 hover 的主要操作。44–48 CSS px 可作为触控设计目标；不要把它误称为所有 Web WCAG AA 场景的统一硬性尺寸。
- 原生：按平台采用 iOS 44pt、Android 48dp 等点击目标建议；可扩大命中区而保持图标尺寸，不能把 pt/dp/CSS px 相互替换。
- 手机：主要操作可达、软键盘不遮住输入、系统返回/安全区、竖横屏和必要的手势替代。
- 平板：按任务设置分栏、内容宽度与导航，不能只是放大手机页面。
- 工业大屏/自助终端：记录真实尺寸、分辨率、缩放、观看距离、站姿与戴手套情况。按设备实测确定物理点击尺寸、间距和可达区域；没有实机时标为待验证。

共同检查：滚动与拖动冲突、拖动取消、重复提交、加载反馈、误触、确认/撤销，以及适用的空白、错误、离线、成功和权限状态。模拟视口只证明布局；合成 touch 事件与实机操作分别注明证据。

## 本地规则评审

读取 `vendor/impeccable/skills/impeccable/reference/` 中与问题相关的文件：`audit.md`（实现质量）、`craft-floor.md`（基础工艺）、`adapt.md`（设备）、`distill.md`（精简）、`polish.md`（精修）。原生使用对应 `.native.md` 和平台文件。参考其检查维度，按 APDR `DesignReviewReport` 组织结果，不声称执行了上游完整 critique。

配合 `vendor/refero/skills/refero-design/references/anti-ai-slop.md`，检查：

- 配色、字体和信息密度是否能解释为本产品的需要。
- 重复卡片、装饰渐变、无意义编号/图标是否掩盖信息层级。
- 用户看到的是否是真实内容；占位内容有无明确标记。
- 动效是否响应操作、提供反馈，且支持减少动态效果。
- 页面是否偏离已批准的设计方向、组件状态或品牌规范。

原始反模板清单包含主观禁用规则。品牌要求的紫色、深色、卡片、衬线字体等都可能合理；不要为消除“AI 味”机械替换品牌、删掉有用信息或牺牲触屏可用性。

每条问题记录位置、可观察现象、用户影响、建议、证据类型与严重度。静态规则、视觉判断、浏览器扫描、合成触控和实机结果分别标注。主观审美建议不等同于可用性缺陷，也不输出“AI 检测准确率”。

## 已安装 detector 与完整 critique

上游 launcher 和当前 Mac 的 `0.1.18` 引擎已安装。优先用 `node scripts/design-tools.mjs detect <source-path> --json` 调用本地引擎；入口核对固定 SHA-256 后直接运行，不在调用时下载程序。没有安装其他平台的二进制，不新增自动 hook。

Web 代码交付的设计审查/质量评估可对本次源文件运行 detector，保存版本、目标、原始输出并审阅误报；复用同版本已有结果。纯设计规格、文案小改或原生任务按实际范围选择，不强行扫描整个项目。不要把未运行 detector 写为“自动检测通过”。源码扫描与浏览器 URL 扫描的覆盖不同；原生源文件不能用 Web detector 的空结果证明通过。

`detect` 退出码：0=完成且无主要发现，2=完成且有发现，1=扫描未完成/失败。不能把 2 当成工具故障，也不能把部分扫描当作完整通过。`critique`（视觉与可用性评审）、`audit`（实现质量）、`distill`（精简）、`polish`（精修）的原始 playbook 均保留在上游 reference 目录；它们是由 agent 执行的方法，不是 detector 自动输出的设计结论。

如用户明确要求上游完整 `critique`，先读取 `reference/critique.md`，遵循其双评估、子代理授权、工具和降级报告要求。APDR 默认本地单评审与此完整工作流分开命名，避免混淆。

已有可运行页面沿用 preview 的 `local_tools_status`、`list_browser_tools`、`run_browser_checks` 和 `audit_accessibility`，参数以工具返回为准。保留 APDR 人工门禁，只复用同版本、同页面状态的证据。
