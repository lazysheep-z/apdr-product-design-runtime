# Product Quality

本技能沉淀通用方法。不得加入操作者资料、真实客户、业务项目名称、账号、私有链接、业务数据、原始日志或截图。产品中的抽象角色与权限模型可以保留；真实身份不能用作示例。

## 按任务读取

- 需求分析、PRD、用户流：读取 [产品规则](references/product-rules.md)，将适用规则写入当前 artifact 的验收条件。
- UI 设计、设计审查、前端增量修改：读取 [界面回归](references/ui-regression.md)，以已确认规范和实际源码为准。
- 版本测试、交接、quality_eval：读取 [测试与证据](references/testing-evidence.md)，提供覆盖清单与逐项结论。
- 纯文案/文档只检查内容与交付；不要求生成页面或运行浏览器。

## 执行边界

1. 明确本次交付、版本、环境、允许的读写范围与验收条件。复用已确认条件；不要将某个历史项目的颜色、字段、层级、日期或审批习惯设为所有产品的默认规则。
2. 独立审查既有产品时，记录现有基线和缺失产物；可以写 draft 审查报告，不创建虚假的完整流水线，不补造审批。
3. 修改前定位拥有该行为的源码、确认文件最新状态并保留可回退基线；修改共用组件时扩大到实际受影响页面和状态的回归。
4. 分开记录检查完成、问题修复、复测通过、人工批准和正式上线。测试分数不能抵消未解决的重大问题或必测路径缺口。
5. 本地前端存储、mock 权限和演示数据只能证明原型层行为；API、服务端权限与生产验收分别取证。

## 回写与放行

现有 13 阶段保持不变。对应阶段 skill 和 playbook 必须引用本技能；通过 MCP 保存当前 artifact。`DesignReviewReport` / `QualityReport` 的 `passed` 必须为布尔值，失败报告不能批准。可选 `verification` 字段结构见 [测试与证据](references/testing-evidence.md)；提供该字段时，引擎会校验必测项、未解决重大问题和版本关联。未提供该字段的历史报告保留兼容，但仍须显式 `passed=true`。

只读审查报告的通过范围由 scope 限定，不能用它替代未执行的完整产品验收。任务要求修复时，按授权修复并复测；只要求审查时报告问题，不擅自改产品。
