# 测试与证据

## 版本测试

先明确环境与授权边界，编写可审阅用例；复用当前会话已给予的执行授权。生产默认只读，写入真实数据须明确授权。授权测试数据变更应记录基线、执行和恢复结果；无权限或无法恢复时写阻塞，不伪造成功。

用例按功能/优先级记录测试数据、操作与预期，复杂操作一步一行；审核状态与执行状态分开。状态至少区分通过、失败、阻塞、未执行、不适用。报告时间使用已约定时区，保留实际精度，不编造历史时间。报告模板优先遵循当前项目约定，不将特定文档或排版写死在框架中。

## 覆盖矩阵

功能/验收条件 → 路由或组件 → 视口/角色/状态 → 操作路径 → 预期与实际 → 结论与证据。主页面、二级详情、弹窗、行内编辑和完整保存流程分别计数。打开表单不能计入保存闭环；抽样操作不能称全量业务验收。

重点覆盖日期初始化与重置、筛选真实结果、树表去重与比率、菜单/缓存返回、保存/刷新/日志、有效与空数据导出、任务重下、权限与失败路径。导出须捕获实际文件并校验类型、表头、数据范围与内容；不能将 CSV 改后缀视为 XLSX。任务重下比较文件内容/哈希，并说明本地原型存储的能力边界。

## 证据和结论

- 记录被测产物 SHA-256、版本、测试时间/时区、范围、操作和项目相对证据路径。修订后旧证据过期；相同版本与状态已有证据可以复用。
- 区分源码推断、自动实测、人工确认和待确认规则；缺陷记录复现、预期、实际、影响、修复与复测。外部缺陷编号只有实际创建后才能称已提交。
- 控制台/Vue/网络错误、axe violations 和 incomplete 都纳入结果；没有错误只能说明已执行范围。
- 可记录 0–100 分质量评分，但 `passed=true` 还必须满足当前范围的必测项通过、无未解决 critical/major 问题、证据对应当前版本。被排除的功能应在 scope 中明确，不能标为通过。
- 缺少审批产物或实际后台时，写独立 draft 审查及能力边界；不代替阶段审批。报告写入 artifact 后再汇报完成。

## 可执行校验结构

`DesignReviewReport.content` 和 `QualityReport.content` 可增加 `verification`：

```json
{
  "sourceSha256": "<当前交付文件SHA256>",
  "testedSha256": "<被测文件SHA256>",
  "scope": "当前验收范围",
  "checks": [
    { "id": "save-reload", "required": true, "status": "passed", "evidence": ["evidence/save-reload.json"] },
    { "id": "native-only", "required": false, "status": "not_applicable", "reason": "本次交付不包含原生应用" }
  ],
  "issues": [
    { "id": "minor-layout", "severity": "minor", "status": "open" }
  ]
}
```

状态为 `passed|failed|blocked|not_executed|not_applicable`；不适用必须非必测并写原因。问题状态为 `open|fixed|verified`，critical/major 只有 verified 才算解除；fixed 尚待复测。校验器检查版本关联、非空范围、唯一检查编号、通过项相对证据路径和未解决严重问题。路径检查不证明文件内容真实，报告作者仍须核对证据。历史报告不提供 verification 时不执行结构校验；`passed` 必须显式为 true 才能批准。
